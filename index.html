Stage 2, Formally — What a Reranker Is

Given a query q and a short-list D1 = {d1, …, dk1} from the first-stage retriever, a reranker is a function

sθ: (Q × D) → ℝ parameters θ

that assigns a real-valued score to each (q, d) pair. The pipeline's stage-2 output is the top-k2 documents ordered by score:

D2 = argsortd ∈ D1↓ sθ(q, d)   [: k2]

Two implementation families dominate:

Cross-encoder

sθ(q,d) = hhead( BERTθ([CLS] q [SEP] d) )

One full transformer forward pass per (q,d) pair. Maximum quality, maximum cost.

Late-interaction (ColBERT family)

sθ(q,d) = Σi maxj ⟨ Eqi, Edj ⟩

Per-token embeddings stored; scoring is a MaxSim reduction. Lower cost; precision close to a cross-encoder on most benchmarks.

This deck derives both, the loss functions that train them, the contrastive loss that trains the bi-encoder feeding stage 1, the distillation trick that lets the bi-encoder inherit the cross-encoder's quality, and the metrics that measure all of it.

02

Cross-Encoder Architecture — Where Tokens Meet

A cross-encoder is the same transformer block you already know, applied to a concatenated input. The mathematics is unremarkable; the consequence is enormous.

The input and the scoring head

x = [CLS] q1 q2 … q|q| [SEP] d1 d2 … d|d| [SEP] H(L) = TransformerStackθ(EmbedTokens(x)) H(L) ∈ ℝ(|x|+3) × D sθ(q,d) = wT H(L)CLS + b scalar score from [CLS] embedding

The reason it works: every-token-attends-to-every-token

Inside each layer, self-attention computes

Attn(H) = softmax( Q KT / √d ) V Q, K, V = HWQ, HWK, HWV

where Q, K, V mix all rows of H — query tokens, document tokens, and special tokens. Concretely, the i-th row of Q KT contains the dot products between token i and every other token. If i is a query token and j is a document token, the entry (QKT)i,j is a direct, learned, soft-aligned similarity between them. The transformer then refines this in every subsequent layer.

Token-level interactions — the bi-encoder doesn't have them

A bi-encoder pools q and d into single vectors before they ever meet. By the time the dot product happens, all token-level structure has been crushed into a global summary. A cross-encoder keeps token-level structure all the way through and scores from a jointly-conditioned [CLS] embedding. This is why cross-encoders win on the BEIR average by 5–10 NDCG points despite using the same backbone architecture.

Cost — the price of those interactions

Per (q, d) pair, the dominant cost is self-attention over |q| + |d| tokens:

cost ≈ L · ((|q| + |d|)2 · D + (|q| + |d|) · D2) L = layers, D = hidden dim

For a 12-layer, 768-dim model with |q|+|d|=384, that is ~1–5 ms on an A100. Multiplied by k=100 candidates, the budget pressure that drives every other decision in this deck.

03

ColBERT — Late Interaction and MaxSim

ColBERT (Khattab & Zaharia, SIGIR 2020) found a middle ground: keep per-token embeddings, but replace full cross-attention with a much cheaper interaction. The cost: a single, simple operator called MaxSim.

The MaxSim score, formally

Let Eq ∈ ℝ|q| × D and Ed ∈ ℝ|d| × D be the L2-normalised token-level embeddings produced by the same BERT-style encoder. The score is:

s(q,d) = Σi=1|q| maxj=1|d| ⟨ Eqi, Edj ⟩

Operationally: for each query token i, find the most similar document token j (over all j), take the similarity, and sum across query tokens.

Why this is “late interaction”

The query and document are encoded independently (cheap, parallelisable, document side cacheable). They only meet at the final MaxSim, which is a closed-form algebraic operation — not another neural network. A bi-encoder interacts at a single scalar (the dot product of pooled vectors). A cross-encoder interacts continuously across all L layers. ColBERT interacts once, per token pair, at the end — hence “late”.

Why MaxSim approximates cross-attention well — and where it doesn't

For each query token, MaxSim selects the single best-matching document token. This captures the most common signal in retrieval — the existence of a strong local alignment — without modelling the joint reasoning across query tokens. The empirical result: on BEIR-class corpora, ColBERTv2 (Santhanam et al., NAACL 2022) closes most of the gap between bi-encoder and cross-encoder quality at a fraction of the cost.

What it misses: conjunctive evidence requiring multiple query tokens to bind to coherent document regions. If a query is “X causes Y under condition Z”, MaxSim can match X, Y, Z to three different documents within the corpus by stitching together their best matches in different paragraphs. A cross-encoder can refuse that — its joint attention can spot that X, Y, Z need to co-occur.

Cost — orders of magnitude cheaper at large k

For reranking a candidate set of k documents:

  • Encoding: one bi-encoder pass per doc, precomputable. Query: one bi-encoder pass total (not per doc).
  • Scoring: for each (q, d), one |q| × |d| dot-product matrix and a row-wise max–sum reduction. Trivially batched on GPU.

End-to-end at k=200: typically 30–60 ms on a single A10, versus 150–300 ms for a comparable cross-encoder. PLAID (Santhanam et al., CIKM 2022) extends this with centroid-based pruning for first-stage use over the whole corpus, but the reranker case shown here needs none of that machinery.

04

Learning-to-Rank — The Three Families

Once the scoring function sθ is chosen, we have to train it. Learning-to-rank (LTR) is the body of methods that turns labelled (query, document, relevance) data into gradient signal. The classical taxonomy is three families, distinguished by what they treat as a training example.

Pointwise

Each (q, d) pair is one example. Predict the label (regression or classification) and minimise per-pair loss.

L = Σ ℓ(sθ(q,d), y)

Simple, but ignores the fact that we only care about the relative order of documents per query, not absolute scores. Used in early TREC systems; rare today.

Pairwise

Each example is a pair of documents (d+, d−) for the same query, with d+ known to be more relevant. Loss penalises the order being wrong.

L = Σ ℓpair(s(q,d+), s(q,d−))

The dominant family. RankNet (slide 05) and contrastive losses (slide 07) live here.

Listwise

Each example is the entire ranked list for a query. Loss is computed over the whole list at once.

L = Σ ℓlist( s(q, ·), y(q, ·) )

Best aligned with metrics like NDCG, but most metrics are non-differentiable. Workaround: LambdaRank (slide 06) — pairwise gradients weighted by metric impact.

The non-differentiable metric problem

What we actually want to optimise — NDCG@10, MRR, MAP — involves sort() and argmax, neither of which is differentiable. The pointwise family ignores this and hopes per-pair regression correlates with rank quality. The listwise family confronts it head-on (smoothed surrogates, listwise softmaxes). The pairwise family in its LambdaRank/LambdaMART form found the pragmatic answer: use a pairwise gradient, then weight it by how much swapping the two documents would change the metric. The next two slides spell that out.

05

RankNet — The Pairwise Workhorse

RankNet (Burges et al., ICML 2005) is the original probabilistic pairwise ranking loss. Most modern reranker training — including cross-encoder fine-tuning — is RankNet or a close cousin.

The model

For a query q and two documents di, dj, let si = sθ(q, di) and likewise sj. RankNet posits a sigmoid model for “di outranks dj”:

Pij = Pr[ rank(di) < rank(dj) ] = σ(si − sj) = 1 / (1 + e−(si − sj))

Let P̄ij ∈ {0, ½, 1} be the target (1 if di is more relevant, 0 if less, ½ if tied). Cross-entropy loss:

Cij = − P̄ij log Pij − (1 − P̄ij) log (1 − Pij)

In the typical “di strictly more relevant” case (P̄ij = 1), this collapses to:

Cij = log(1 + e−(si − sj)) softplus margin loss

The gradient — clean and useful

Differentiate the cross-entropy form with respect to si:

∂Cij / ∂si = σ(si − sj) − P̄ij and ∂Cij / ∂sj = −(∂Cij / ∂si)

Define

λij ≡ ∂Cij / ∂si = σ(si − sj) − P̄ij

Then the total gradient on score si from a query's pair set is:

∂C / ∂si = Σ{j : (i,j) ∈ pairs} λij − Σ{j : (j,i) ∈ pairs} λji

These λs are the “lambdas” that name LambdaRank. They are signed forces on each score: positive lambda ⇒ push score up; negative ⇒ push down.

Hard negatives matter most

From the gradient form: λij = σ(si − sj) − 1 when di should outrank dj. If the model already gets it right by a wide margin (si ≫ sj), σ≈1 and the gradient is near zero — nothing to learn. If the model gets it wrong (si < sj), the gradient is near −1 — full force. Therefore: training is gradient-dominated by the hard pairs — the close calls and the actual mistakes. This is why hard-negative mining (pick negatives that the current model scores near the positive) is the central trick in modern reranker training.

06

LambdaRank & LambdaMART — Optimising the Metric

RankNet treats all pair-order errors as equivalent. NDCG does not. A swap of positions 1 and 2 hurts NDCG much more than a swap of positions 99 and 100. LambdaRank (Burges, Ragno & Le, NIPS 2006) fixes this by weighting each pairwise gradient by the metric impact of swapping that pair.

The LambdaRank gradient

Take the RankNet lambda and multiply by the magnitude of the metric change if the two documents swapped positions in the current ranking:

λij(LR) = ( σ(si − sj) − P̄ij ) · | ΔNDCGij |

where ΔNDCGij is the change in NDCG if documents i and j swap rank positions (all other documents fixed). This can be computed analytically from the rank positions and the labels:

ΔNDCGij = (Gi − Gj) · (1/Di − 1/Dj) / IDCG

where Gi = 2reli − 1 (gain) and Di = log2(ranki + 1) (discount) — see slide 09 for the full DCG definition.

A heuristic that became canonical

LambdaRank's gradient is not the gradient of any obvious loss function. Burges et al. introduced it as a heuristic: if we could differentiate NDCG, this is roughly what the gradient would look like. Later work (Donmez, Svore & Burges 2009; Wang et al. 2018) proved that LambdaRank gradients are in fact gradients of an underlying smooth surrogate for NDCG — the heuristic was a real algorithm in disguise. The practical result is the same: state-of-the-art on LETOR and TREC benchmarks for over a decade.

LambdaMART — LambdaRank gradients inside a GBDT

LambdaMART (Wu, Burges, Svore & Gao, 2010) takes the same lambdas and uses them as the residuals in gradient-boosted decision trees (MART = Multiple Additive Regression Trees):

  1. Initialise scores s(0) = 0.
  2. For boost round t: compute λij for every pair under the current ranking; aggregate per-document λi; fit a regression tree to predict λi from feature vector xi; update s(t+1) = s(t) + η · tree(x).
  3. Stop when validation NDCG plateaus.

LightGBM and XGBoost both ship a lambdarank objective that implements exactly this. For production rerankers operating over handcrafted features (BM25 score, dense cosine, click-through rate, freshness, recency …), LambdaMART remains the algorithm to beat. For end-to-end neural rerankers, the LambdaRank gradient idea is implemented inside SBERT-style training loops as MarginRankingLoss or with explicit listwise reweighting.

InfoNCE — Training the First-Stage Bi-Encoder

The bi-encoder that feeds stage 1 is also a ranker; it just has to be cheap. Modern dense retrievers (DPR, E5, BGE, GTE, Voyage) are trained with a contrastive loss called InfoNCE — a listwise softmax over one positive and many negatives.

The loss

For a batch of queries with positive documents and negatives, define the similarity

s(q, d) = ⟨ fθ(q), gφ(d) ⟩ / τ τ = temperature, often shared with φ

The InfoNCE loss for a triple (q, d+, {d−k}) is:

L = − log   es(q, d+) / ( es(q, d+) + Σk es(q, d−k) )

This is exactly cross-entropy with the positive as the “correct class”: maximise the softmax probability that the model assigns to the positive document among (d+, d−1, …, d−N).

Where the negatives come from

  • In-batch negatives. For every query in a batch, the other queries' positives serve as “easy” negatives. Free signal; bigger batch ⇒ more contrast ⇒ better embeddings. This is why dense-retrieval training runs at the largest batch size that fits on the hardware.
  • Hard negatives. Documents that look superficially relevant but aren't. Mined by running a current bi-encoder over the corpus and taking high-scoring non-relevants. Repeating this every few epochs (“iterative hard-negative mining”) is the central trick behind BGE, GTE, and E5.
  • Curated hard negatives. For Q&A datasets (MS MARCO, NQ), “BM25 negatives” (top-100 BM25 non-positives) are a standard, model-independent source.
Why temperature matters

The temperature τ sharpens or softens the softmax. Small τ (e.g. 0.05) makes the loss focus aggressively on the hardest negative; large τ (e.g. 1) gives every negative similar weight. Tuning τ is one of the highest-leverage hyperparameters in contrastive retrieval — the trade-off is between learning sharp discriminative features (small τ) and stable training (larger τ).

Connection to pairwise RankNet

The InfoNCE softmax over (d+, d−1, …, d−N) can be rewritten as a sum of pairwise terms involving s(q,d+) − s(q,d−k) — structurally the RankNet loss with one positive per group and N negatives. InfoNCE is, modulo normalisation, the listwise version of RankNet over a hand-picked candidate slate.

MarginMSE — Distilling a Cross-Encoder into a Bi-Encoder

Cross-encoders are the gold standard for relevance but cannot run on the whole corpus. Bi-encoders can run on the whole corpus but are less accurate. Can the bi-encoder learn from the cross-encoder?

Yes. The trick is knowledge distillation with a loss tailored for rankers: MarginMSE (Hofstätter, Althammer, Schröder, Sertkan & Hanbury, arXiv 2010.02666, 2020).

The loss

Let sT be the teacher (cross-encoder) score and sS the student (bi-encoder) score. For a triple (q, d+, d−):

MT = sT(q, d+) − sT(q, d−) teacher margin MS = sS(q, d+) − sS(q, d−) student margin LMarginMSE = ( MS − MT )2

Why the margin, not the score

Distilling the absolute scores would force the bi-encoder to match the cross-encoder's score magnitudes — impossible, because the two architectures have different output distributions. The margin — the gap between positive and negative — is the rank-determining quantity. Teaching the student to reproduce the teacher's margins teaches it to reproduce the teacher's rankings without forcing it to reproduce the teacher's score scale.

Why this works so well

A cross-encoder trained on millions of (q, d+, d−) triples has implicitly learned the relevance manifold. Its margin MT on a fresh triple is a much richer label than the binary “positive vs negative” tag — it encodes the degree of relevance difference. Training the student on margins is closer to regression on a continuous teacher signal than to binary classification. Empirically: distilled bi-encoders match cross-encoder NDCG@10 to within 1–3 points on most benchmarks, at bi-encoder cost.

Practical recipe

  1. Train (or pick) a strong cross-encoder teacher on MS MARCO + your domain data.
  2. For each (q, d+, d−) triple in the training corpus, run the teacher and cache MT.
  3. Train the bi-encoder with LMarginMSE, often combined with InfoNCE so the bi-encoder also gets contrastive signal: L = α·LInfoNCE + β·LMarginMSE.
  4. The BGE and BGE-M3 model families are trained with this combination; their reranker counterparts serve as the teachers.

Evaluation — DCG, NDCG, MRR, MAP

All the loss functions above are surrogates. The metrics that actually decide whether a system shipped are these four. Each is defined per query and averaged over the eval set.

DCG — Discounted Cumulative Gain

For a ranked list of k documents with graded relevance labels rel1, …, relk:

DCG@k = Σi=1k (2reli − 1) / log2(i + 1) industry / TREC formula

Two pieces of intuition:

  • Gain (numerator). 2reli − 1 is exponential in the label — a label-3 document is much more valuable than three label-1 documents combined. (Järvelin & Kekäläinen's original 2002 formula used reli linearly; the exponential form is the modern default.)
  • Discount (denominator). log2(i+1) down-weights positions further down the list. Position 1 has discount log2(2) = 1; position 10 has log2(11) ≈ 3.46; position 100 has log2(101) ≈ 6.66. Logarithmic discount captures “users look at top results much more than later ones” without crashing to zero.

NDCG — Normalised DCG

DCG depends on the number of relevant documents and label distribution per query — raw DCG values are not comparable across queries. Fix: normalise by the DCG of the ideal ranking (relevant docs sorted by label, in order):

NDCG@k = DCG@k / IDCG@k ∈ [0, 1]

NDCG@10 is the de facto BEIR-style benchmark metric for retrieval and reranking.

MRR — Mean Reciprocal Rank

For each query, find the rank of the first relevant document; take its reciprocal; average over queries:

MRR = (1/|Q|) · Σq 1 / rankq(first relevant) 0 if none in top-k

Right metric when there is one canonical answer per query (single-answer Q&A, fact lookup). Tells you nothing about ranking quality beyond the first relevant result.

MAP — Mean Average Precision

For each query, compute Average Precision (AP):

AP@k = (1 / Rq) · Σi=1k Precision@i · [di relevant]

where Rq is the total number of relevant documents for q and the indicator gates the sum to relevant positions. Then MAP = meanq APq. MAP uses binary relevance; rewards both finding many relevant docs and ranking them high.

Which metric for which job

NDCG@10 — default for everything; graded relevance, position-aware, comparable across queries. MRR — single-answer pipelines (factoid QA, codesearch, GitHub-issue retrieval). MAP — multi-document retrieval with binary labels; standard on TREC-style ad-hoc retrieval. Recall@k — the right metric for stage 1 of the cascade specifically (slide 05 of Deck 08).

The circular relationship

The reranker (stage 5) becomes the teacher for the next iteration's distillation (stage 4). The improved bi-encoder (stage 4 output) becomes the source of harder hard negatives for the next iteration's contrastive training (stage 3) and for fine-tuning the next reranker (stage 5). This iterative loop is how BGE-v1 became BGE-M3 and how the GTE-Qwen and E5-mistral series scaled their quality without scaling their parameter counts.

What to Take Away

  • A reranker is just a scoring function sθ(q, d). The two production families — cross-encoder and ColBERT MaxSim — differ only in where the query and document tokens interact and how much that interaction costs.
  • MaxSim is a strict relaxation of full cross-attention. Each query token picks its single best document match, independently. Cheap, parallel, indexable; misses joint multi-token reasoning. Right answer for most reranking at scale.
  • The three LTR families correspond to three views of the data: pointwise (one pair), pairwise (two docs for a query), listwise (all docs for a query). Pairwise dominates because gradients are easy and hard negatives provide the signal.
  • RankNet's lambda is the building block. A signed force on the score; magnitude depends on how wrong the current ranking is. Hard negatives produce big lambdas; correctly-ranked easy negatives produce near-zero gradient.
  • LambdaRank weights lambdas by |ΔNDCG|. Errors near the top hurt the metric more, so push the optimiser harder on them. LambdaMART is the same idea inside GBDT — still SOTA for tabular-feature reranking.
  • InfoNCE is the listwise softmax over a positive and many negatives — how every modern dense bi-encoder is trained. Temperature and hard-negative quality are the two highest-leverage hyperparameters.
  • MarginMSE distillation transfers cross-encoder quality to bi-encoder cost. Match the margin, not the absolute score — that is the rank-determining quantity and the only thing the student can plausibly reproduce.
  • NDCG@10 is the universal target. Position-weighted, exponential-gain, normalised. MRR for single-answer, MAP for binary multi-relevant, Recall@k for stage 1.
